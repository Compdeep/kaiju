Kaiju · Architecture

An executive kernel,
for secure execution.

Kaiju is not a general assistant. It is designed to run alongside the operating system, interfacing directly with core system functions to carry out administrative tasks and operational workflows.

Every capability is exposed through securely gated tools. Actions are not executed implicitly: each request is interpreted for intent, scoped to the minimum required access, and then passed through explicit controls before it runs. This ensures that operations are traceable, constrained, and verifiable at every step.

Built in Go with a deliberately small dependency surface, Kaiju is designed to be predictable, auditable, and reliable in environments where correctness matters.

It does not sit above the system as a helper. It operates alongside it, as a controlled execution layer for real work.

impact ≤ min(intent, clearance, scope)
The one rule every side-effecting action must pass before it runs — the tool's impact can never exceed what the request asked for, what the caller is trusted for, or what the scope allows.
Every decision is audited — allow or deny
A blocked action is written to the log and never runs; an allowed one is written with its outcome. There is no unrecorded action.
No ambient data between steps
A step reads a prior step's output only through an explicit ${step.N} edge. Nothing leaks in implicitly — the data path is the declared graph.
Small core, heavy things isolated
One static Go binary. PDF parsing and the JavaScript-rendering web reader are build-tag plugins or an out-of-process host, so the default binary links neither their code nor their dependencies.

These four hold for every request — there is no fast path that skips the gate, the audit, or the edge model. They are enforced in the core execution path, not by convention.

01

Life of a request

Follow one request from arrival to answer. The numbered spine is the journey; each card is one stop. Nothing with a side effect runs until it clears the gate at step 5.

Caller
Request arrives
A query or alert reaches the single gateway on :8090 over an authenticated session. A JWT identifies the principal and carries its tool allowlist and an intent ceiling — deny by default: a tool absent from the scope is invisible.
1
Preflight
Classify & scope
One light-model call decides chat, meta, or investigate. Chat short-circuits to a direct reply. Investigate also picks the few relevant guidance skills (capped) and the intent the plan will need.
2
Executive
Plan the DAG
The executive makes one call to emit a plan: a DAG of tool steps, each step wired to earlier ones by ${step.N} references. Broken wiring — a self-reference, a missing producer — is rejected and re-planned before anything runs. See §02.
3
Scheduler
Fire node batches
Every step whose dependencies are done fires at once, as its own goroutine. Independent steps run concurrently; a step's typed output feeds its dependents through the ${step} wiring. This is the parallelism spine.
4
IGX gate
Gate every action
Before a tool runs, the triad gate checks impact ≤ min(intent, clearance, scope). A read-only step (impact 0) always passes; anything that writes, kills, or controls must clear on all three. A block is audited, never silent. See §04.
5
Execute
Run the tool
The tool runs — bash, file_*, web_*, compute, service, or a plugin — sandboxed to the workspace. Its result is a typed envelope (ok / empty / error), and empty is first-class, so absence is never mistaken for content.
6
Reflection
Continue, replan, conclude
After each batch a reflector decides. Replan grows the graph to repair a failure (via a root-cause debugger) or to expand the search. A conclusion cannot fire while a structural precondition is unmet — e.g. concluding without reading the sources it found.
7
Aggregate
Synthesize the answer
The aggregator streams a final answer built only on what was gathered. "Edge" reframes make gaps explicit — failed or empty steps, the exact URLs a search returned — so it acknowledges absence instead of fabricating to fill the shape of the request.
8
Return
Stream & record
The answer streams back token-by-token over SSE, filtered per-principal so one caller never sees another's events. The run is recorded, and its full DAG trace is snapshotted server-side for the frontend.
9
Audit
Audit the decisions
Along the way every gate decision was written to the audit log: the tool, its impact, the intent and clearance in force, and allow or block. That trail — not the model's word — is the record of what the system was permitted to do.
10

This is the interactive path, end to end, and it runs today. The same engine also serves a planner-less chat lane (a direct reply, no tools) and a ReAct loop, selected per request. The rest of this document opens up each stage: the DAG engine (§02), the gate (§03), the tools (§04), and the plugin, routing, memory, and lifecycle machinery around them.

02

Graphed execution

The run as a whole is a loop, not one acyclic graph — reflection can replan, and a repair cycle can graft new work, so execution comes back around. But within each planned execution it is a directed acyclic graph: typed nodes whose edges are data dependencies, run the way a build system runs a Makefile — everything that can run in parallel does, and each node waits only for the outputs it actually needs. Below is the whole orchestration: circles are nodes, lines are edges, and every node type that can appear in a run.

One run. Preflight classifies, the executive plans a DAG, nodes fire in node batches wired by ${step} dependency injection, a reflector loops (replan) or ends it (conclude), a failure detours through the debugger → Holmes → micro-planner and grafts a fix, and the aggregator streams the answer. Observer and interjection steer from the side.

Every node, what it is

PRE
Preflight
One light-model call: chat / meta / investigate, the relevant skills, and the intent ceiling. Chat short-circuits; investigate proceeds.
EXE
Executive
The planner. One heavy call emits the DAG of steps (and, on a replan, grows it). Broken ${step} wiring is rejected before the run.
TOOL
Tool
A single capability invocation — bash, file_*, web_*, service, a plugin. Gated by IGX, returns a typed envelope.
CMP
Compute
A coder model writes a real script, kaiju runs it sandboxed, stdout flows back into the graph — for precision or a library a model can't do in its head.
RFL
Reflection
After each batch (and at quiescence): continue, replan, or conclude. A diminishing-returns brake keeps it from looping.
OBS
Observer
A lightweight watcher that can continue, inject a step, cancel, or ask for a reflection — bounded by its own budget.
INJ
Interjection
A human message sent into a running query. It becomes the next reflection's focus, steering the run without restarting it.
DBG
Debug
The repair entry-point. A failure grafts a debug super-tool step that opens a root-cause cycle instead of blindly retrying.
HOL
Holmes
A ReAct root-cause loop: it investigates the failure — reads logs, inspects state — and produces a diagnosis, not just a stack trace.
MPL
Micro-planner
Turns the diagnosis into a concrete fix, grafts it as new nodes, and re-arms the stored validators so a fixed failure stops being re-reported.
AGG
Aggregator
Synthesizes the final answer from the gathered evidence and streams it token-by-token. Skipped when the reflector's verdict already stands.
ACT
Actuator
An optional recommended follow-up action the aggregator can surface (a suggested next step), distinct from the tools it ran.

From plan to graph

The executive emits steps; two passes turn them into a live graph. The ${step.N.field} references are the edges — a fetch reads the URL a prior search produced. Wiring that can't resolve is caught before the run, and the planner gets one correction round with the exact fault.

1 Plan call
One heavy-model call, the plan tool-choice pinned so even a weak model must emit structured steps. Each step is a tool, its params, its depends_on, and a tag.
executive · heavy lane
steps returned
2 Edge validation
Every ${step.N.field} is checked against the plan and the producing tool's output schema. Three mis-wirings are rejected: a step that reads its own output, an out-of-range index, and a wrong producer — reading results[].url off a web_fetch, when only web_search makes a result list.
validatePlanEdges
clean, or one re-plan with the fault
3 Build the graph
Steps become nodes; depends_on resolves to node IDs (never self-wired), and each ${step.N} rewrites to ${node.<id>} so the dispatcher can resolve it from a dependency's real output at run time.
planStepsToNodes
graph ready
4 Batches
The scheduler fires every node whose deps are terminal, as concurrent goroutines, then blocks for completions and repeats. Independent nodes share a batch; dependent ones chain. A per-tool throttle and a node/LLM/per-skill budget bound the blast radius.
scheduler loop

Node types beyond plain tools: compute (an LLM writes and runs a real script when precision or a library is needed), reflection and observer (steer the run), and a repair pipeline — a debug super-tool spawns a Holmes root-cause loop, a micro-planner grafts the fix, and stored validators re-check it, so a fixed failure stops being re-reported. The plan is grown by replan, never rewritten from scratch.

Edges — why it doesn't make things up

An "edge" is a gated reframe on the hand-off between steps: a small amount of code collects the structural facts (which gather steps came back empty, which URLs a search actually returned), and a short LLM pass frames them so the next step treats absence as absence.

Every edge is gated: a clean run with no gaps pays nothing. Together with the edge validation above, this is the anti-fabrication layer — the planner is kept from inventing wiring, and the aggregator from inventing evidence.

03

Dependency injection

The edges in the graph don't just order the work — they carry data. A node reads an earlier node's output by reference, and the engine injects the real value at run time. This is what lets a whole plan be built before any result exists, and it is checked for soundness before a single node fires.

How a reference resolves

A param can contain ${step.N.field} — "the field of step N's result". It goes through two phases:

Plan time
Each ${step.N.field} is rewritten to ${node.<id>.field} via the step-index → node-id map, and step N is added to the node's dependencies so it can't run first. validatePlanEdges rejects a reference to a step that can't produce it — a self-reference, an out-of-range index, or a field the producing tool's schema never emits — and sends the planner back for one correction.
rewriteStepTemplates
validatePlanEdges
Run time
When the node is ready, the dispatcher resolves ${node.<id>.field} from the dependency's real, typed output. A bare placeholder preserves the value's type (an object stays an object); an embedded one interpolates as text. A dependency that came back empty fails fast rather than injecting nothing.
substituteTemplates

Worked example

A search feeds a fetch. The plan names the wiring; the engine fills it in once the search returns.

The plan · before any run
# step 0 — produces a results[] list
web_search  query="acme status page"

# step 1 — reads the first result's url
web_fetch   url=${step.0.results.0.url}
           depends_on:[0]
▶
At run time · once step 0 resolves
# step 0's typed output
step 0 → { results: [
    { url: "https://acme.io/status" },
    … ] }

# step 1's url, injected
url = "https://acme.io/status"

web_search declares a results[] output; web_fetch does not. So the plan above is valid, but the reverse — a web_fetch reading ${step.N.results.0.url} off another web_fetch — is caught at plan time as a wrong-producer edge and re-planned. Sound wiring is a precondition of running, not something discovered by failing. See §02 for where this sits in the flow.

04

Intent-Gate Execution

This is the heart of kaiju's security posture, and the reason it can be trusted with a shell. Every tool call is graded by the side effect it would actually have, and that grade is checked against three independent ceilings. If any one of them sits below the action's impact, the action is refused — and the refusal is audited.

Impact — graded per call

Impact is not a property of a tool, it is a property of this invocation. bash is capable of anything, but bash("ls") is read-only — the gate sees the real effect of the actual params, not the tool's worst case.

Observe
impact 0 · always passes
Read-only. Inspect files, list processes, search and read the web, recall memory. No state changes, nothing created — never gated.
Affect
impact 100 · the default working level
Reversible side effects. Write a file, run code, install a dependency, start a service, edit configuration — where real work happens.
Control
impact 200 · requires elevation
Destructive or irreversible. Kill, force, wipe, uninstall. Reached only by process_kill and a destructively-classified bash/git.

The tiers are configurable, not hardcoded — seeded from config into a database, extensible with custom ranks. The three shown (observe 0, operate 100, override 200) are the built-in ladder.

The triad — three ceilings, all must hold

impact  ≤  min( intent, clearance, scope )

Intent

What the plan may attempt. Set at preflight from the request and capped by the caller's ceiling — a read-only question can't quietly plan a destructive step.

preflight → capped

Clearance

The node's standing authority — the rank the engine itself is cleared to. An optional external endpoint can be asked per tool, and it fails closed: unreachable means deny.

node rank · fail-closed

Scope

The caller's per-tool ceiling, from the JWT and a database. Deny by default: a tool not in your scope isn't merely blocked — it is invisible to the planner in the first place.

JWT + DB · deny-by-default

The gate runs at dispatch, not planning — so it sees the real params. impact 0 always passes; a global lockdown blocks everything above it at once; and every decision, allow or block, is appended to an audit log with the tool, its impact, and the three ceilings in force. Authority is never asserted by the model — it is enforced by the kernel and recorded.

05

Skills & tools

Everything the agent can do is one of two things: a tool it calls to act on the world, or a skill that shapes how it plans and works. Tools are capabilities; skills are guidance. Both are picked for the request and both are cheap to add.

Skills — guidance, not capability

A handful of skills relevant to the request are chosen at preflight and folded into the prompts. Two kinds:

Guidance skills

Markdown SKILL.md playbooks. The relevant ones inject their ## Planning Guidance / ## RULES into the executive, and their coder/aggregator guidance where those run. A skill that declares a command-dispatch instead becomes a real callable tool.

skillGuidance · hot-reloaded

Capability cards

A small set of embedded cards — data_retrieval, general_reasoning, self_awareness, system_operations — with named sections the executive, aggregator, and compute pull from. Additive, always available.

capabilities · embedded

Selection happens once, at preflight: the query is matched against the union of cards + skills, de-duplicated, and capped, and the choice rides on the graph so concurrent runs never clobber each other. Full detail in the skills reference.

Tools — the catalogue

Every capability is a Tool with one job and a per-invocation impact — bash("ls") is graded 0 even though bash can reach Control. ~30 built-ins live in one in-process registry, each returning a typed envelope (ok / empty / error — empty is first-class, so "found nothing" is a real outcome). To the planner, a compiled tool and one a plugin added at runtime are indistinguishable.

Tools may also declare an output schema, which is what makes the ${step.N.field} wiring (§03) checkable before a run, and a display hint, which pushes a result panel to the frontend. Full catalogue in the tools reference.

06

Plugins

The core stays small on purpose. Anything heavy — a PDF parser, a headless browser — is opt-in and lives outside the default binary. There are two ways in, and both land in the same tool registry, so the planner never has to care which is which.

compiled · in-process
pdf
a Go build-tag plugin; adds pdf_extract and teaches web_fetch to read PDFs
remote · out-of-process
webreader
a Python host over REST; adds web_read, rendering JavaScript pages when a plain fetch is thin
built-in
office_extract
pure-stdlib .docx/.pptx/.xlsx — no dependency, so it needs no plugin at all

Compiled plugins

Registered from an init() behind a build tag, so the default binary links neither the plugin nor its heavy library. It contributes a tool and/or a seam that enriches web_fetch — the pdf plugin does both.

-tags plugin_pdf

Remote bridge

A generic REST bridge to an out-of-process host. It reads the host's manifest and synthesizes one kaiju tool per advertised tool — so adding a plugin to the host needs no kaiju rebuild. A stalled host can never hang a run: every call is capped at 60s, then web_fetch falls back to its built-in reader.

-tags plugin_remote

The host: one gateway, per-service queues, supervised

The out-of-process host is one process that fronts every remote plugin. Plugins load once and stay warm — a browser pool, a loaded model — across calls. Concurrency is enforced where the state lives:

Per-service queue
Each plugin has its own concurrency limit (webreader serves 4 reads at once). All of a plugin's calls share one queue; different plugins have independent queues, so a slow render never blocks another service. Overflow waits for a slot.
host · semaphore/plugin
Supervised
Kaiju runs the host through its own service manager, not an external supervisor — tracked, health-checked every 10s, auto-restarted on crash. Before every spawn the port is cleared, so exactly one instance can ever bind; port-conflict skip and fast-crash backoff stop restart loops.
service manager
Self-healing
Enabling verifies real tools registered, not a stale flag — so a host that died after boot heals instead of lying. On startup, any configured remote capability is reconnected and, if down, relaunched. The reader survives a kaiju restart and a host crash without a human.
enable · boot self-heal
07

Model routing

One request touches several models, each on the job it does best. A request carries a model selection, never a key — keys live only in config — and an unselected lane falls through to the engine default, so routing is invisible until you use it.

Heavy
The reasoning lane: the executive planner, the aggregator, validators, root-cause analysis. Where thinking happens.
a.llm
Light
The cheap lane: classify, reflect, preflight, observe, compact. Small, fast, and frequent.
a.executor
Answer
Kept separate so a user's thinking answer-model writes the final reply without ever being handed the planner's forced tool calls.
answer lane
Vision
A direct image lane, plus an image_read tool; a request's images attach only to a model that can actually see.
vision lane

Providers speak two wire protocols — OpenAI-compatible (which covers OpenRouter and any self-hosted endpoint) and Anthropic. An org or user chooses which models are enabled and the defaults per lane; a user may override the reasoning model only. Every non-streamed call passes one token-accounting chokepoint, so spend is metered. A raw /oneshot completion bypasses the whole agent — the passthrough a compliance host uses for its own model stage.

08

Memory & sessions

Memory is deliberately walled off. It is reachable only at the chat boundary — where a human is talking to the system — and never from inside the execution layer. A tool result cannot read or write memory, which shuts the door on prompt-injection carried in gathered content. This is the single most important property of the subsystem, so the wall is drawn first.

Chat boundary

Where a human message enters and an answer leaves. History and long-term memory are read, written, and folded into the system prompt for the turn at this boundary — and nowhere else.

no memory access
Execution layer

The DAG, the tools, the models reasoning over gathered text. It cannot reach your conversation history or long-term memory — so a malicious web page or uploaded file can neither read your history nor inject a false long-term "memory" into a later turn.

Two distinct stores

"Memory" is really two separate stores — easy to conflate, so they're worth separating:

Conversation & long-term · SQLite

The memory manager: sessions and messages, plus a long-term store of semantic / episodic / procedural entries namespaced per user. Owner-scoped, loaded and injected at the chat boundary.

internal/memory + internal/db

Agent key-value · JSON

A separate flat JSON store that the memory_store / memory_recall / memory_search tools read and write — the one sanctioned way the agent itself touches memory, distinct from the DB manager above.

internal/agent · memory.json

The memory types

Within those stores are five kinds, each scoped and used differently. Definitions, namespaces, and how facts are extracted are in the memory reference.

Short-term
Per-session conversation history — every message in the thread.
sessions + messages
Semantic
Per-user, cross-session facts — "prefers Python", "prod DB is db.internal:5432".
memories · {user}/semantic
Episodic
Per-user, cross-session experiences — "the last migration took 45 min", "that deploy broke".
memories · {user}/episodic
Procedural
Per-user self-modifying instructions — the namespace is reserved, not yet used.
memories · {user}/procedural

How history is served

The same conversation is presented differently depending on who's asking, and trimmed so a long session stays affordable.

Planner
Gets a truncated history — long assistant and user turns clipped head-and-tail — so the plan has context without drowning the window.
LoadHistory

Gets the recent turns verbatim, untruncated, because a conversational reply needs the exact words.

A bounded set (~20 semantic + 10 episodic) is folded into the system prompt as a "Your Memory" block — at the chat boundary only.

Past a threshold (~30 turns), all but the last ~10 are summarized by the model and replaced with a "[Conversation summary]" so the window stays bounded.
Compact

Two safety properties fall out. Tenant isolation: the memory manager is constructed per-request and scoped to the caller, so one principal's history and memory are never visible to another. Restart resilience: a run killed mid-flight leaves a question with no answer, which the UI reads as "still running" forever — so on boot, kaiju reconciles those dangling turns with a terminal note (§09). Full detail in the memory reference.

09

Run lifecycle

A long run is not a black box. It can be steered while it runs, stopped for real, or quietly superseded by a newer message — each with a distinct, deliberate mechanism.

Stop
The Stop button cancels the job's context, which unwinds the DAG — pending nodes drop, the aggregator is skipped. This is a real teardown: a client simply disconnecting only stops the caller waiting, while the worker keeps running. Stop cancels the work itself.
/stop → job.cancel()
Interject
A message sent into a running query. It becomes the primary focus of the next reflection — steering the run without restarting it, and never spawning a second query.
/interject
Preempt
A newer message for a session whose job is still queued supersedes the old one — newest wins. If that session's job is already running, the newer message is routed as an interject instead, so a running query is never abandoned mid-flight.
scheduler
Reconcile
A run killed by a process restart gives no cleanup code a chance to run. On the next boot, kaiju closes out any turn left dangling, so a restart never leaves a session's progress bar spinning forever.
boot

What runs where

A small footprint. The engine is one Go process; the only other moving part is the optional plugin host, which kaiju supervises itself. Model providers are the only thing outside the perimeter, and they hold no keys of their own.

core
Kaiju
:8090 · Go
The single gateway and the whole engine — auth, the DAG scheduler, the IGX gate, the tools, memory, SSE, and the embedded web UI.
supervised
Plugin host
:8092 · Python
The optional out-of-process host (webreader). Localhost-only, warm, per-service queued, and kept alive by kaiju's own service manager.
embedded
SQLite
file · WAL
Sessions, messages, memory, the audit log, intents and scopes — one embedded database file, no server.
external
Providers
OpenAI · Anthropic · …
The models. Keys are held by kaiju, never the browser; a request carries only a selection.

Everything with a side effect is inside the core process and passes the gate; the audit log is the record of what it was permitted to do. Kaiju runs standalone, or embedded as the reasoning engine behind a compliance host such as makeen, which fronts it with identity, redaction, and oversight. Either way the contract is the same: identity and control on the outside, gated execution on the inside.
